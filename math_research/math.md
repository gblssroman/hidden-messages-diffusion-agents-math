# Задание для Романа: Hidden Messages для математики

## Цель

Реализовать систему из двух диффузионных языковых агентов, которые совместно решают математические задачи и обмениваются скрытыми сообщениями во время генерации. Сообщение — компактное представление промежуточных скрытых состояний отправителя, которое влияет на дальнейшее решение получателя.

Проверить два режима: **разделённое условие**, где агентам нужны сведения друг друга, и **полное условие у обоих**, где один агент предлагает ход решения, а второй формирует окончательный ответ. Главный результат — воспроизводимый прототип и сравнение способов коммуникации; улучшение точности предстоит проверить.

Основа — [статья Hidden Messages](/Users/a.gazzaev/Desktop/48_Hidden_Messages_Between_Dif.pdf), раздел 3 и приложение A.

## Модели

В каждом эксперименте использовать двух агентов на одной модели с независимыми контекстами и состояниями генерации.

| Модель | Checkpoint | Назначение |
|---|---|---|
| **Tiny-A2D, 0.6B** | [Qwen3-0.6B-diffusion-mdlm-v0.1](https://huggingface.co/dllm-hub/Qwen3-0.6B-diffusion-mdlm-v0.1) | Отладка канала, арифметика и короткие задачи с разделёнными условиями |
| **Dream-7B** | [Dream-v0-Instruct-7B](https://huggingface.co/Dream-org/Dream-v0-Instruct-7B) | Основные эксперименты на текстовых математических задачах |

Начать с замороженных весов моделей и обучаемых модулей коммуникации. Использовать канал из статьи: четыре вектора размерности 128, residual fusion для Tiny-A2D и виртуальный префикс для Dream. Обучить канал на математических задачах; начальный вариант обучающего сигнала — masked-token loss по целевому ответу или решению из train. Готовый канал для QASC не считать обученным для этой задачи.

## Основные данные

| Набор | Что сделать |
|---|---|
| **Собственный микро-набор** | Сгенерировать арифметические цепочки и простые уравнения с условиями, разделёнными между агентами. Например, A знает `a` и `b`, B знает `c` и должен найти `(a+b)·c`. Подготовить точные ответы и пары с изменённым числом только у A |
| **[GSM8K](https://github.com/openai/grade-school-math)** | Основной набор текстовых арифметических задач. Из официального train выделить обучение и dev; test использовать для итогового сравнения. Дополнительно подготовить фиксированный срез с разделёнными исходными условиями |
| **[MATH](https://huggingface.co/datasets/EleutherAI/hendrycks_math)** | Использовать официальный train для обучения канала Dream и разработки; начать с prealgebra и algebra. Dev выделить из train |
| **[MATH-500](https://huggingface.co/datasets/HuggingFaceH4/MATH-500)** | Итоговая проверка Dream на 500 задачах из MATH. Это тестовый поднабор, его нельзя использовать для обучения или настройки |

В синтетике разделить train/dev/test по семействам шаблонов; варианты одной задачи и контрфактические пары держать вместе. Проверить дубликаты и пересечения обучающих данных с оценкой. MATH-500 входит в MATH-test, поэтому не считать их независимыми бенчмарками.

При разделении GSM8K распределять только исходные факты задачи, сохраняя вопрос и необходимые обозначения. Проверить, что объединённое условие сохраняет смысл и ответ, а получателю действительно недостаёт информации. Эталонное решение не использовать для подсказок или разбиения на подзадачи при оценке. Результаты изменённого среза сообщать отдельно от исходного GSM8K.

## Обязательные сравнения

| Вариант | Реализация |
|---|---|
| **Один агент, полное условие** | Решает исходную задачу; проверяет способность модели при наличии всей информации. Дать сопоставимый вычислительный бюджет, при необходимости — дополнительный проход самопроверки |
| **Два агента без сообщений** | Работают независимо с теми же входами и ролями, что в режиме общения |
| **Два агента с текстовыми сообщениями** | Передают промежуточные вычисления и предложения решения текстом |
| **Два агента со скрытыми сообщениями** | Передают обученные векторные представления во время генерации — исследуемый метод |
| **Локальный адаптер** | Модуль той же архитектуры обучается только на собственных состояниях получателя; контролирует пользу дополнительных обучаемых параметров |

Заранее назначить агента B получателем, чей итоговый ответ оценивается во всех многоагентных вариантах. Не выбирать лучший ответ по эталону и не добавлять голосование. Для каждого режима фиксировать входные сведения, роли, веса моделей, лимиты попыток и сопоставлять затраты обучения и генерации. В первом прототипе агенты работают без калькулятора и внешнего решателя; проверяющая программа доступна только оценщику.

Обязательные проверки скрытого канала: **отключение** и **подмена сообщением другой задачи** с другим ответом. На микро-наборе также изменить существенное число у отправителя и проверить ожидаемое изменение ответа получателя. При вмешательстве фиксировать контекст, состояние и генератор случайных чисел получателя до доставки сообщения. Передача через общий текстовый журнал или общую память в обход канала исключается.

## Порядок экспериментов

1. **Воспроизвести канал на Tiny-A2D.** Проверить передачу сообщения и совпадение режима без канала с базовой моделью.
2. **Подготовить микро-набор.** Проверить одного агента с полным условием; если задачи почти не решаются, упростить их на dev до обучения коммуникации.
3. **Провести все сравнения на Tiny-A2D.** Обучить канал и локальный адаптер, выполнить отключения, подмены и направленные изменения условий на фиксированном test.
4. **Повторить микро-эксперимент на Dream.** Сравнить один поздний обмен с несколькими обменами во время решения.
5. **Перейти к GSM8K на Dream.** Обучить канал на train и сравнить методы отдельно на исходных задачах с полным условием у обоих агентов и на срезе с разделёнными условиями.
6. **Добавить MATH.** Обучить канал на MATH-train, зафиксировать настройки по dev и провести итоговые сравнения на MATH-500 с полным условием у обоих агентов.

Основная метрика — **доля правильных итоговых ответов за одну попытку**. Для чисел использовать нормализацию и точное сравнение; для выражений — фиксированный проверяющий модуль, например [Math-Verify](https://github.com/huggingface/Math-Verify). Отдельно учитывать ошибки извлечения ответа; правильный ответ сам по себе не доказывает корректность всех рассуждений. Дополнительно измерять время, GPU-секунды, число проходов модели и объём сообщений; сравнивать методы на одинаковых задачах.
